BÀI 3: PHÂN TÍCH TÀI CHÍNH - TÍNH TOÁN CHI PHÍ AI
1. TÍNH TOÁN CHI PHÍ CƠ BẢN (VÀO / RA)

Khối lượng token hàng ngày:
- Input: 10.000 hóa đơn x 1.500 tokens = 15.000.000 tokens/ngày = 15M
- Output: 10.000 hóa đơn x 500 tokens = 5.000.000 tokens/ngày = 5M

MÔ HÌNH A (DeepSeek Chat - Direct API)
  Input:  15M x $0.14/1M  = $2.10
  Output: 5M x $0.28/1M   = $1.40
  Ngày:   $3.50
  Tháng:  $3.50 x 30 = $105.00

MÔ HÌNH B (OpenRouter - Gemini 2.5 Flash)
  Input:  15M x $0.075/1M = $1.125
  Output: 5M x $0.30/1M   = $1.50
  Ngày:   $2.625
  Tháng:  $2.625 x 30 = $78.75

=> Về chi phí thuần: Model B rẻ hơn Model A (đặc biệt do giá Input thấp hơn
gần một nửa). Chênh lệch ~$26/tháng.

2. CHI PHÍ ĐIỀU CHỈNH MÔ HÌNH B KHI TÍNH LỖI 0,5% + RETRY 5%
- Tỉ lệ lỗi 0,5% khiến retry làm tăng thêm 5% tổng token đầu vào hàng ngày.
- Input điều chỉnh: 15M x 1,05 = 15,75M tokens/ngày.
  Chi phí Input mới: 15,75M x $0.075/1M = $1.18125
- Output không đổi: $1.50

  Ngày (điều chỉnh): $1.18125 + $1.50 = $2.68125 (~$2.68)
  Tháng (điều chỉnh): $2.68125 x 30 = $80.4375 (~$80.44)

Kết luận: dù tính cả lỗi + retry, Model B vẫn rẻ hơn Model A (~$80.44 so với
$105.00/tháng, tiết kiệm ~$24.56/tháng). Giả định: retry chỉ tốn thêm token input
theo đúng dữ kiện đề bài; nếu retry cũng sinh thêm output thì chênh lệch hẹp lại
nhưng B vẫn có lợi.

3. PHÂN TÍCH KỸ SƯ GIẢI PHÁP - YẾU TỐ PHI TÀI CHÍNH

MÔ HÌNH A (Direct API - DeepSeek)
- Ưu: Gọi thẳng nhà cung cấp, con đường ngắn nhất -> Latency thấp và ổn định.
  SLA trực tiếp với DeepSeek, dễ đàm phán, cấu hình đơn giản, ít lớp trung gian.
- Nhược: Vendor lock-in DeepSeek (khó đổi model khi giá/quality đổi). Rủi ro
  điểm lỗi đơn lẻ: khi DeepSeek down là hệ thống ngừng ngay. Không linh hoạt
  chuyển sang Gemini/Claude khi cần.

MÔ HÌNH B (Aggregator - OpenRouter)
- Ưu: Không lock-in vào một nhà cung cấp, đổi model chỉ bằng config (phù hợp
  chiến lược hybrid AI của bài 1). API chuẩn OpenAI dễ tích hợp. Có thể dự phòng
  nhiều nhà cung cấp trong một aggregator.
- Nhược: Thêm một lớp trung gian -> Latency cao hơn và thêm điểm chịu lỗi
  (lỗi 0,5% phải retry). SLA phụ thuộc aggregator, giá/biến phí có thể thay đổi,
  rate limit dùng chung, khó cam kết độ ổn định như vendor trực tiếp.

QUYẾT ĐỊNH ĐỀ XUẤT (DỰ ÁN LÂU DÀI)
- Nếu ưu tiên chi phí + linh hoạt đa model: chọn B (rẻ hơn kể cả sau retry,
  tránh lock-in).
- Nếu ưu tiên độ ổn định + latency thấp tuyệt đối: chọn A.
- KHẢ THI NHẤT: Kiến trúc lai "Multi-Provider": dùng B làm primary (chi phí +
  linh hoạt), A làm fallback khi B lỗi/vượt SLA, kèm caching kết quả JSON cho
  các hóa đơn trùng định dạng để giảm số request. Vừa tối ưu chi phí vừa giảm
  rủi ro lock-in và điểm lỗi đơn lẻ cho hệ thống lâu dài.
